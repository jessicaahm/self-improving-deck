Self-Improving Deck

Two Claude agents generate and refine an HTML presentation deck, orchestrated by a single Temporal workflow — with a human-in-the-loop feedback cycle that survives worker crashes, failed model calls, and reviewers who take days to reply.

02 Architecture

Three processes: the Temporal server holding the event history, a worker running the workflow and its activities, and your terminal sending the workflow start, the feedback, and the approval. Claude is reached only from inside activities — never from workflow code, which must stay deterministic.

Every failure case

The fourteen cases the markers above point at — where each one strikes, what goes wrong, and the mechanism that handles it.

Failure pointFailure descriptionSolution
Deck.run() — the workflow
Case 1query(prompt) → Claude✗ Claude Agent SDK Retries exhausted. generate_deck fails on every attempt — a network error, ClaudeAgentFailed, or an empty result. Retry policy gives 3 attempts (5s → 10s backoff). The write is .tmp + os.replace, so no partial deck is ever visible. After attempt 3, saga.compensate() runs delete_deck(delete_all=True) and the run FAILS with nothing on disk.
Case 2query(prompt) → Claude✗ Claude Agent SDK Terminal error. Claude reports "Not logged in" — no amount of retrying will fix it. _as_temporal_error maps it to ApplicationError(type="Unauthorized", non_retryable=True), which is listed in non_retryable_error_types. Attempts 2 and 3 are skipped and compensation runs at once, saving ~35s of pointless backoff.
Case 3wait_condition(approved)✗ Deck.run() The human never responds. A plain script cannot wait hours for a reviewer, and cannot survive a restart while it waits. wait_condition(approved, timeout=3m) is a durable timer in the event history — the worker can restart mid-wait and it still fires. On expiry the run raises ApprovalTimeout, drains in-flight handlers, then delete_deck(delete_all=True) removes deck, backup and .tmp.
Case 4execute_activity(generate_deck)✗ Activity worker The worker dies mid-activity. generate_deck sends no heartbeats, so Temporal cannot tell a slow Claude call from a dead process. start_to_close=5m bounds the damage: at 5 minutes the attempt is failed and retried. On restart the workflow replays from history — saga.add is re-applied deterministically and no completed activity is re-run. (Compare Case 10, detected in ~30s.)
Case 5signal: approve Approval lands while a revision is still running. A naive workflow would return while Claude is still writing to the deck. finally: wait_condition(all_handlers_finished) holds the workflow open until the update handler completes. The deck is never cut off half-way; without it Temporal logs an unfinished-handler warning.
Case 6approval timer fires Same race as Case 5, but on the timeout path — the deadline expires mid-revision. The same finally applies. The handler finishes (or fails and runs restore_deck), and then the run's delete_deck wipes everything. Both sagas unwind, LIFO within each.
Case 7workflow cancelled A cancel request is delivered as asyncio.CancelledError inside run(). Caught by except (Exception, asyncio.CancelledError), so delete_deck still runs. Note that submit_feedback's except Exception does not catch it — a revision in flight skips restore_deck, but delete_deck cleans up regardless.
Case 8workflow terminated Terminate stops the workflow at the server without running any workflow code at all. None. No saga runs; the deck, the backup and any .tmp files are left on disk. This is the one failure mode Temporal cannot help with — prefer cancel over terminate.
submit_feedback() — the update handler
Case 9acquire the revision lock Data corruption. Two feedback updates arrive together and would both edit the same deck. asyncio.Lock serialises them: B waits for the whole of A's revision — the amber band above — and revision_status reports locked=true meanwhile. B's snapshot is taken after A finishes, so rolling B back lands on A's deck, not the original.
Case 10execute_activity(revise_deck)✗ Activity worker The worker dies mid-edit, leaving the deck half-revised on disk. A naive retry would apply the feedback twice, on top of a partial edit. Heartbeats every 2s with heartbeat_timeout=30s detect it in ~30s. Each attempt resets the deck from the snapshot before Claude edits, so the feedback is applied exactly once. snapshot_deck is not re-run on replay, so the backup stays the true baseline.
Case 11update: submit_feedback(...)✗ submit_feedback() Wrong sequence of events. Feedback arrives before the deck exists, or the feedback text is blank. validate_feedback rejects the update before the handler body runs: no lock is taken, no activity is scheduled, and a rejected update leaves no events in history — so the caller can simply resend once generation completes.
Case 12query(prompt, tools=…) → Claude✗ Claude Agent SDK Terminal error during revision — Claude is not logged in. Same Unauthorized rule as Case 2: retries are skipped and saga.compensate() runs restore_deck. The update FAILS but the workflow stays alive, parked on the approval timer.
Case 13query(prompt, tools=…) → Claude✗ Claude Agent SDK Retries exhausted. All 3 attempts of revise_deck fail, each one having reset from the snapshot first — so the deck is left holding the last attempt's half-edit. saga.compensate() runs restore_deck, copying the snapshot back over the deck. It returns to its pre-feedback state, the workflow stays alive, and the next feedback snapshots a clean baseline.
Case 14execute_activity(snapshot_deck)✗ Activity worker The snapshot itself fails. snapshot_deck is fast file I/O but can still hit a disk or permissions error, and is retried 3×. If its retries are exhausted, saga.add(restore_deck) was never reached, so compensate() is a no-op — which is correct, because the deck was never touched. The update FAILS and the deck is unchanged.

04 How to run it

You need a Claude Code subscription (the Agent SDK uses it instead of API billing) and the Temporal CLI installed. Four terminals is the comfortable setup: server, worker, starter, feedback.

1

Create the environment

python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
2

Start the Temporal dev server

temporal server start-dev   # UI at http://localhost:8233
3

Start the worker

Registers the Deck workflow and all five activities on greeting-task-queue.

cd agents
python worker.py
4

Start a run

Prints a fresh workflow ID like deck-workflow-96853fe5 — every run gets its own, so you can re-run without an ID clash.

python app.py
5

Send feedback, then approve

Feedback is an update (it waits for the revision and returns a result); approval is a signal (fire-and-forget).

python feedback.py deck-workflow-96853fe5 \
  --feedback "Add a first slide called '2 You' with a picture of a flower"

python feedback.py deck-workflow-96853fe5 --approve
6

Inspect while it runs

# is a revision currently holding the lock?
temporal workflow query --workflow-id deck-workflow-96853fe5 --type revision_status

# full event history
temporal workflow show --workflow-id deck-workflow-96853fe5 --detailed
To see durability live: start a run, kill the worker with Ctrl+C while generate_deck or revise_deck is in flight, then start python worker.py again. The workflow resumes from the last completed activity — no repeated Claude calls — and revise_deck rewinds the deck to its snapshot before retrying, so the feedback is applied exactly once.

The generated deck lands at agents/output/deck_<workflow_id>.html — a self-contained single file with no external CSS or JS. Open it in a browser.

05 Tech stack

Three dependencies, one server, one model.

temporalio
Python SDK for Temporal. Provides durability, visibility into every step, atomic activity orchestration, and the primitives the saga pattern is built on — signals, updates, queries, timers, retry policies and heartbeats.
claude-agent-sdk
Runs both agents. Chosen over the API client SDK for cost — it runs against a Claude Code subscription, so you must be logged in (claude auth login). Generation runs tool-free and returns raw HTML; revision gets Read/Edit/Write with permission_mode="acceptEdits" so it edits the deck in place.
aiofiles
Async file I/O, so reading the source content and writing the deck never blocks the worker's event loop.
Temporal dev server
Runs locally on localhost:7233 via temporal server start-dev, with the Web UI on :8233. Holds the event history that makes replay possible.
claude-sonnet-5
The model behind both the generate and revise activities.
Python 3.13
Plain dataclasses cross the workflow/activity boundary, which keeps arguments backwards-compatible as the schema evolves; asyncio.Lock serializes concurrent revision handlers.

Patterns implemented in the code itself

Idempotency

Writes go to a .tmp file then os.replace — atomic, so a retry can never observe a half-written deck. revise_deck restores from the snapshot at the start of every attempt.

Saga

Saga.add() registers delete_deck before generation starts, so any run-level failure cleans up whatever got created; compensate() unwinds LIFO and keeps going if one compensation fails. Revision rollback is handled inside the activity instead.

Terminal vs. retryable

Unauthorized is listed as non-retryable, so a logged-out Claude fails fast into compensation instead of burning three backoff attempts.
