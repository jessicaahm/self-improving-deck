Self-Improving Deck

Two Claude agents generate and refine an HTML presentation deck, orchestrated by a single Temporal workflow — with a human-in-the-loop feedback cycle that survives worker crashes, failed model calls, and reviewers who take days to reply.

Temporal Claude Agent SDK Durable execution Human-in-the-loop Saga / compensation Python 3.13

01 What this repository is about

Generating a deck and iterating on it with human feedback sounds like a simple script — until you run it in a distributed environment where the worker can crash, the model can fail mid-edit, and the human can take days to respond. This repo is a teaching demo: a deliberately small domain used to make durable-execution problems concrete.

Without durability

A crash loses everything

A plain script holds its state in memory. Kill it halfway and the expensive LLM call, the half-edited file, and the knowledge of what already succeeded all disappear.

Without durability

A process can't wait for a human

Review may come hours or days later. No ordinary process stays alive that long, and nothing records the pending request if it dies.

With Temporal

Progress is checkpointed

Every activity result lands in the event history. Restart the worker and completed steps replay from that history — Claude is never called twice for work already done.

With Temporal

Waiting is free and durable

workflow.wait_condition(lambda: self.approved) parks the workflow with no process running. The approval signal unblocks it whenever it arrives.

Four areas the demo covers

Interaction

Signal vs. update vs. query; update validators; handler concurrency and locks.

Detection

Start-to-close timeouts; activity heartbeats; retryable vs. terminal errors.

Recovery

Idempotent activities; saga compensation; durability and deterministic replay.

Foundation

Workflow sandbox and determinism; workflow-ID reuse policy; schema evolution.

The deck is a stand-in. In production the same shape shows up wherever a multi-step, side-effecting process needs human sign-off — transferring funds, confirming a travel booking, publishing a change.

02 Use cases the repo exercises

Each scenario is a scripted failure or race you can reproduce live. Green means it has been run end-to-end; amber means it is wired up but not yet demonstrated.

Happy path
passed
Approve before generation finishes
The signal sets approved early; the workflow still finishes generating, then completes with the deck saved.
passed
Feedback sent before the deck exists
The update validator rejects it — "Deck not generated yet" — without touching workflow state.
passed
Approve while revise_deck is running
The wait unblocks, but all_handlers_finished keeps the workflow from completing mid-revision — the in-flight edit finishes first.
passed
Approve while generate_deck is running
The signal sets approved while the activity is still in flight; the wait consumes it as soon as generation returns.
Saga / compensation
passed
Generate → revise → approval times out
The outer saga unwinds and delete_deck(delete_all=True) removes the deck, the backup and any temp files.
passed
Revise fails after logging out of Claude
A non-retryable Unauthorized error fails on attempt 1. Because revise_deck rewinds from the snapshot before calling Claude, the deck is left at its pre-feedback state.
Durability
passed
Kill the worker mid-generation, restart it
Temporal re-queues the activity; the restarted worker picks it up and the run continues into revision.
Concurrency
passed
Two feedback updates arrive at once
asyncio.Lock serializes them: A runs, B waits, then B applies on top of A's result. revision_status reports {"locked": true} while A holds the lock.
Idempotency
passed
Kill the worker after a partial edit, then retry
revise_deck resets the deck from the snapshot at the top of every attempt, so the feedback is applied exactly once instead of stacking on a half-finished edit.

03 Architecture

Three processes: the Temporal server holding the event history, a worker running the workflow and its activities, and your terminal sending the workflow start, the feedback, and the approval. Claude is reached only from inside activities — never from workflow code, which must stay deterministic.

    04 How to run it

    You need a Claude Code subscription (the Agent SDK uses it instead of API billing) and the Temporal CLI installed. Four terminals is the comfortable setup: server, worker, starter, feedback.

    1

    Create the environment

    python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
    2

    Start the Temporal dev server

    temporal server start-dev   # UI at http://localhost:8233
    3

    Start the worker

    Registers the Deck workflow and all five activities on greeting-task-queue.

    cd agents
python worker.py
    4

    Start a run

    Prints a fresh workflow ID like deck-workflow-96853fe5 — every run gets its own, so you can re-run without an ID clash.

    python app.py
    5

    Send feedback, then approve

    Feedback is an update (it waits for the revision and returns a result); approval is a signal (fire-and-forget).

    python feedback.py deck-workflow-96853fe5 \
  --feedback "Add a first slide called '2 You' with a picture of a flower"

python feedback.py deck-workflow-96853fe5 --approve
    6

    Inspect while it runs

    # is a revision currently holding the lock?
temporal workflow query --workflow-id deck-workflow-96853fe5 --type revision_status

# full event history
temporal workflow show --workflow-id deck-workflow-96853fe5 --detailed
    To see durability live: start a run, kill the worker with Ctrl+C while generate_deck or revise_deck is in flight, then start python worker.py again. The workflow resumes from the last completed activity — no repeated Claude calls — and revise_deck rewinds the deck to its snapshot before retrying, so the feedback is applied exactly once.

    The generated deck lands at agents/output/deck_<workflow_id>.html — a self-contained single file with no external CSS or JS. Open it in a browser.

    05 Tech stack

    Three dependencies, one server, one model.

    temporalio
    Python SDK for Temporal. Provides durability, visibility into every step, atomic activity orchestration, and the primitives the saga pattern is built on — signals, updates, queries, timers, retry policies and heartbeats.
    claude-agent-sdk
    Runs both agents. Chosen over the API client SDK for cost — it runs against a Claude Code subscription, so you must be logged in (claude auth login). Generation runs tool-free and returns raw HTML; revision gets Read/Edit/Write with permission_mode="acceptEdits" so it edits the deck in place.
    aiofiles
    Async file I/O, so reading the source content and writing the deck never blocks the worker's event loop.
    Temporal dev server
    Runs locally on localhost:7233 via temporal server start-dev, with the Web UI on :8233. Holds the event history that makes replay possible.
    claude-sonnet-5
    The model behind both the generate and revise activities.
    Python 3.13
    Plain dataclasses cross the workflow/activity boundary, which keeps arguments backwards-compatible as the schema evolves; asyncio.Lock serializes concurrent revision handlers.

    Patterns implemented in the code itself

    Idempotency

    Writes go to a .tmp file then os.replace — atomic, so a retry can never observe a half-written deck. revise_deck restores from the snapshot at the start of every attempt.

    Saga

    Saga.add() registers delete_deck before generation starts, so any run-level failure cleans up whatever got created; compensate() unwinds LIFO and keeps going if one compensation fails. Revision rollback is handled inside the activity instead.

    Terminal vs. retryable

    Unauthorized is listed as non-retryable, so a logged-out Claude fails fast into compensation instead of burning three backoff attempts.
