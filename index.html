Self-Improving Deck

A Temporal durable-execution demo where two Claude agents collaboratively generate and refine an HTML presentation deck, with a human-in-the-loop feedback loop that survives crashes, restarts, and multi-hour waits.

What This Project Showcases

The Problem: Fragile AI Pipelines

LLM calls are expensive

If a multi-step AI pipeline crashes mid-way, you lose all progress and repeat costly API calls.

Human feedback takes time

A reviewer might take hours or days to respond. A simple script can't wait that long — the process dies.

No crash recovery

Plain Python scripts lose all state on failure. No checkpointing, no replay, no retries.

No observability

When something fails in an AI pipeline, it's hard to know what succeeded, what failed, and where to resume.

The Solution: Temporal + AI Agents

Durable execution

Temporal checkpoints after each activity. Kill the worker, restart it — the workflow resumes from the last success. No repeated LLM calls.

Long-lived waits

wait_condition persists in Temporal's event history. The process can reboot and the workflow still unblocks when a signal arrives — even days later.

Automatic retries

Activities retry with exponential backoff on failure. Rate limits, network blips, API errors — all handled automatically.

Full event history

Every activity input, output, signal, and state transition is recorded. Replay exactly what happened, debug any failure.

  1. Start the workflow (python starter.py)
  2. Kill the worker mid-activity (Ctrl+C)
  3. Restart the worker (python worker.py)
  4. Observe: the workflow resumes from the last completed activity — no repeated LLM calls

How Temporal Addresses Distributed Systems Challenges

Exactly-Once Execution

Temporal's event history ensures each activity runs exactly once. Completed activities are replayed from history on recovery — not re-executed. This prevents duplicate LLM calls and duplicate side effects.

Deterministic Replay

Workflows must be deterministic — given the same event history, they always make the same decisions. Temporal enforces this via the workflow sandbox, which blocks non-deterministic imports and operations. This guarantees consistent state reconstruction after any crash.

Failure Modes

  • Worker dies: Temporal detects missing heartbeats, reassigns the activity to another worker. The workflow resumes from the last checkpoint.
  • Temporal server dies: Event history is persisted to the database. On restart, all workflows resume from their last recorded state.
  • Network partition: Workers reconnect and poll for tasks. Pending signals and updates are delivered once connectivity is restored.

Scalability

Multiple workers can poll the same task queue. Temporal distributes activities across available workers automatically. To scale, add more worker instances — no code changes needed.

Idempotency

Activities must be safe to retry. In this project, generate_deck writes with mode "w" (overwrite), so running it twice produces the same file. revise_deck edits the existing deck in place — also idempotent.

Saga Pattern & Compensation

If a later activity fails permanently, Temporal does not auto-rollback earlier steps. You own the compensation logic — e.g., if revise_deck fails after 3 retries, you could restore the original deck from a backup. Each activity is its own unit of work; rollback is explicit, not implicit.
